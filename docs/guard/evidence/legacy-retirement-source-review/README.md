The stronger `managed_resident_stop.rs` and `managed_resident_supervisor.rs` files are not part of the reachable module graph. The reachable native stop creates its current digest scope, chooses only the first discovered state, tries an authenticated request, and then waits for containment in that selected scope. Empty discovery and unsuccessful send both return the recorded error. Its discovery helper skips unreadable or invalid generation files; it cannot serve as an exhaustive absence proof. Its state identities record the serving process and exclude the shared owner. A failed startup's `abort_spawned_managed` ignores termination and short containment errors, so a failed launch cannot be treated as guaranteed retirement.

An after-the-fact candidate scan of published state is insufficient for every possible legacy producer. A supervisor may be delayed before publishing a generation, and startup/owner locks can be free before that producer runs. A briefly free home-wide owner lock is not a persistent guarantee against a later launch. The actual process layout also escapes the outer phase process group: Python starts a persistent native client in a new session, and the Rust supervisor creates its own process group. Outer process exit therefore does not establish producer containment. A general native correction needs an actual reachable operation plus complete producer provenance or a process scope that cannot be escaped; adding an unused or current-digest-only helper cannot supply this.

For the narrowly observed protected-cache rejection, a distinct **no new legacy native producers** witness is a credible smaller direction. It must prove nonexistence through a complete execution history, not by inspecting missing files. It must retain the real failed native start, the real native stop exit 2, all previous failed reports, the preceding generation's genuine retirement receipt, protected policy bytes, receipt readbacks and revision floors. This witness would qualify only that negative transition; it would not repair production native idempotent stop.

The proposed parent-only audit hook that rejects every helper cannot pass the normal baseline path. `GuardDaemonServer._begin_owned_service` starts `HookProcessRunner`; its supervisor launches multiprocessing guardians, and each guardian launches an evaluator. A publisher-only native-client counter misses those interpreters. The evaluator constructs its store and HookWorker only after a review message, making the pre-send `_send_review_to_slot` entry a useful additional causal boundary. The `request_exposed` flag is weaker because it is assigned after the send. Final slot maps omit earlier retired workers, and `Process.start()` may create a process before a slot is returned. Every attempt must be accounted for.

The actual phase launches `python -I installed_transition_entry.py`. A spawned guardian or evaluator reimports this lightweight entry as `__mp_main__` before target unpickling/application imports. Installing a passive observer at the entry's top level can cover those interpreters without replacing frozen baseline functions. It must account separately for the pinned standard-library multiprocessing/resource-tracker bootstrap. The `-I` option already excludes user site and `PYTHONPATH`; installed-environment site initialization, dependencies, native extensions and source identities still require an explicit trust boundary.

Python audit hooks operate within one interpreter and are not a sandbox; registration may fail silently when an existing hook rejects it. The witness therefore needs a registration self-test and explicit child coverage. Audit events expose useful process creation calls, but they do not by themselves report successful reaping. These are limits of the observation mechanism, not evidence that any historical producer launched. [Python audit-hook documentation](https://docs.python.org/3.12/library/sys.html#sys.addaudithook), [Python audit event table](https://docs.python.org/3.12/library/audit_events.html).

Passive execution monitoring can observe original function entries and returned results without callable replacement. Python 3.12 monitoring exposes function-start, function-return and exception events; return callbacks receive the returned value. A profile-based alternative must cover the main and all producer threads. In particular, replacing `native_resident_client.run_isolated_hook_process` would change baseline behavior because that module branches on the callable's identity. [Python execution monitoring](https://docs.python.org/3.12/library/sys.monitoring.html), [Python thread profiling](https://docs.python.org/3.12/library/threading.html#threading.setprofile_all_threads).

The smallest defensible next implementation is diagnostic-only:

1. Start a source-pinned observer in the main phase entry and every known spawned interpreter before application construction/imports. Use original call/code identities. Record bounded, synchronous, identity-bound process and thread events. Observation failures mark evidence incomplete and must not raise into or modify the baseline program.
2. Observe every reachable process-creation attempt, exact nonspawning native capabilities/self-test/stop calls and their original bounded completion results, the underlying native-client function, pre-send review entry and shutdown results. A native producer call, unknown command, uncovered child, unaccounted partial start, changed observer or telemetry gap leaves the proof false.
3. Reconcile the entire process history with independently checked identities/exits. A dead unexposed guardian's legacy retirement `true` does not itself prove its evaluator exited. Keep collection active through producer shutdown; missing final records from a killed child must not erase a prelaunch event. Retain all original daemon, runner, publisher and stop results.
4. Emit a separate diagnostic object while the existing `worker_evidence` and `suite_acceptance` gates remain unchanged. Obtain a fresh installed witness. Promote a tagged no-new-producer proof only after source and counterexample review shows complete coverage and the real hosted record satisfies every predicate.

If this diagnostic reveals an uncovered or actual producer, it must remain unverified. A broader native operation would need strict bounded enumeration across all home scopes/generations, authenticated private state and acknowledgements, full executable digest and PID-start identities, explicit unknown-versus-exited results, and complete containment of unpublished processes within the existing deadline. It must also prevent future launches from an unclosed launcher until verification finishes. Filesystem absence alone cannot recover the missing launch history.

`proof-model.json` specifies the required predicates and unresolved boundaries. `test-plan.json` contains 28 proposed source, observer, schema, containment and hosted counterexample tests. `independent-bootstrap-review.md` independently identifies the child-bootstrap and retirement-shortcut gaps. Source archives are lossless gzip; both source hashes and archive hashes are recorded.
