# macOS qualification interpreter provisioning proposal

Source reviewed before implementation, 2026-09-18. The isolated checkout is based on actual public `590ce01334a7724f3f1349b2ab252110a5a268f5`, tree `7284a9c2bf2f301d84a500cafd56a6153785f3cf`. This document proposes a shared disposable-fixture correction; it records no implemented or hosted success.

Both macOS candidate arms in run 35330471726 fail the unchanged installed `validate_regular_file` at line 404 with `codex_hook_interpreter_permissions_unsafe`. ARM job 105553416699/artifact 10540663999 and Intel job 105553416595/artifact 10542180119 report a symlink invocation, regular canonical target, root owner, mode 0775, and a writable group which is neither root nor the current primary group. Their 982-byte failure reports have SHA-256 `a945b268e58b6065ef633010479cf07c3e172ef4aedacfc6db8102b4797e0043` and `468fc0ea49e3e9cf6eaead4083ce60c86973071443c80cc0b58e1c73c01247d8`. These are observations after rejection, not a held-handle attestation of the exact earlier read. The rejection itself is correct under the unchanged validator.

Both actual setup logs select CPython 3.12.10 at `/Library/Frameworks/Python.framework/Versions/3.12/bin/python3.12` and create `.venv` independently in baseline and candidate source directories. The reports do not export the invocation's absolute path or its literal link target. Taken together with the shared builder, they support the inference that the candidate environment retains uv's symlink to the selected framework interpreter. A future provisioning receipt must establish that relationship directly from the owned invocation and canonical source rather than treating this inference as a historical attestation.

The builder runs `uv sync --frozen --extra dev --python 3.12`, builds the immutable wheel, installs that exact wheel, and chooses `.venv/bin/python`. Its provisioning check currently runs only for `x86_64-unknown-linux-musl`. The third installed-transition environment is likewise provisioned only on Linux. All nine relevant source files read for this review are byte-identical between c343 and actual 590; the installed validator is also byte-identical to the frozen 2e module, SHA-256 `ba1375f80db3a8121091e330a8cd1c3c0b36250789267209f8972e23c141ba42`.

Fresh Linux artifact 10542130137 already supplies a passing two-arm provisioning receipt: both 17,752-byte selected executables are copied byte-for-byte, the original target and `pyvenv.cfg` remain unchanged, each copy is an owned regular 0755 file, and each installed unchanged validator passes under isolated execution. Its CPython version is 3.12.14, distinct from the Macs. That receipt proves the existing Linux path, not macOS behavior.

The existing helper is suitable for a bounded macOS attempt because it already:

- Checks owned non-writable venv/bin directories and bounded private `pyvenv.cfg` contents.
- Resolves the selected invocation, opens the regular source without following a newly substituted symlink, and verifies complete metadata before/after the bounded copy.
- Copies at most 128 MiB to a newly owned file, sets that new file to 0755, compares complete source/copy SHA-256, atomically replaces only the private venv invocation, and checks the original target was preserved.
- Compares isolated original/copy version, implementation, ABI, SQLite/OpenSSL, prefix, base prefix and executable binding; the post-copy probe calls the actual unchanged validator from that arm's installed wheel and records its digest.
- Retains a failed arm independently and makes any failed/mismatched pair a required-check failure. Subsequent independent installed checks can still collect their own outcomes.

CPython 3.12.10's non-Windows `venv` implementation supports copying the base executable and making the copy 0755. Its macOS framework launcher locates the actual framework interpreter and preserves the invocation through `__PYVENV_LAUNCHER__`; it deliberately avoids discarding symlink information. These sources support trying an exact-byte copy, but do not replace the real runtime/prefix/validator checks. The invocation copy alone is not a copy or integrity proof of the whole Python framework and shared libraries. [venv source](https://github.com/python/cpython/blob/v3.12.10/Lib/venv/__init__.py), [framework launcher source](https://github.com/python/cpython/blob/v3.12.10/Mac/Tools/pythonw.c).

Proposed smallest correction:

1. Generalize the existing private-copy entrypoint to explicitly supported Linux and macOS platforms, with truthful per-platform receipt scope. Preserve the copy algorithm, source bytes, byte limits, original metadata checks, isolated probes, deadlines, and every failure condition. Keep a compatibility entrypoint if needed for existing Linux callers; do not widen unsupported platforms silently.
2. Select the same required two-arm provisioning operation for both declared macOS targets in the builder. Keep the Linux-only Claude pilot selection independent. Each arm must compare its original/copy runtime and must share identical original interpreter bytes with the other arm. No version substitution, downloading a different Python, source-wheel modification, framework re-signing or root tool-cache mutation is allowed.
3. Apply the same supported-platform selection to the separate owned transition venv after coordinating with the retirement work owner. Its paired installations stay unchanged. A fixture-level correction must not leave the third environment silently selecting the rejected shared executable.
4. Verify the unchanged historical integrity rejection, copy identity/metadata checks, both-arm failure retention, platform selection and runtime-mismatch rejection. Use actual Linux copies for executable tests and exact old/current installed validator modules. Mac dispatch tests are source tests only; do not fake `sys.platform` and describe Linux execution as macOS qualification. Preserve original failed outputs and obtain actual Mac provisioning receipts on a future stable candidate.

The cold metric remains a fresh process and its complete timer boundary. Registered-launcher measurement begins before `run_isolated_hook_process`; native one-shot cold measurement stops the resident and starts its timer before spawning the runtime. Those functions and all fixture startup, corpus, acceptance, iteration and deadline constants stay byte-identical. Provisioning is recorded as installation setup, before the existing paired driver, and supplies no timed decision samples. It must not call hooks, start a daemon/resident, perform DNS warmup, populate decision caches or reuse a measured process. The stdlib/validator installation probes can affect ordinary filesystem cache state, so this cannot be represented as proof of a cold filesystem or a performance benefit.

The two frozen macOS baseline constructor lookup failures are separate and remain failed. Correcting the candidate interpreter fixture cannot erase those failures, qualify the full pair, resolve legacy retirement or satisfy remaining transition/security/review/canary requirements. No production validator exception or host permission change is proposed.
