# Private native Claude launcher pilot

This is a Linux qualification pilot for the existing Claude `PreToolUse` and `PostToolUse` registrations. It adds a command to the already distributed `hol-guard-runtime` binary. Normal installation, SessionStart, other Claude events, other harnesses, frozen Core and the signed Desktop proxy continue through their existing selectors. No default registration selects this command.

The boundary is one registered process from stdin through authenticated daemon transport to final stdout and exit. Python's existing daemon still owns current workspace policy, acknowledged native policy identity, source-reference context, external-source permission, Watch and availability delivery, native evaluation, and approval state. The pilot does not accept a resident envelope or move these decisions into its transport process.

| Contract | Pilot behavior |
| --- | --- |
| Invocation | Absolute installed `hol-guard-runtime claude-hook-pilot --registration PRIVATE_RECORD --event PreToolUse` or `PostToolUse`. Payload and environment do not select the implementation. |
| Registration | Only `scripts/native_claude_launcher_pilot.py::install_private_pilot` selects it, inside an explicitly supplied private qualification root. It reads the existing generated registration, retains all other handlers, and binds the exact final configuration digest and argv. Repeating the private install is idempotent. Restoring the original configuration retires the prior pilot registration. |
| Installation identity | Reuses the private managed-hook manifest secret with the distinct `claude-native-launcher-pilot` purpose of the existing local-authority MAC contract. The daemon discovery key is not copied or used to authorize installation. |
| Runtime identity | Requires the invoked process to be the bound binary; checks file identity, package manifest, runtime/version/protocol/build/rule identity, and the bound Python helper and bridge files. Descriptor opens use O_NOFOLLOW and O_NONBLOCK, so a regular-file-to-FIFO replacement is rejected without waiting for a writer. The opt-in installer also requires actual wheel membership and cleared development overrides. |
| Interpreter | Keeps the original installed invocation path, including a virtual-environment symlink, and separately binds its resolved target and link identity. |
| Transport | Uses one explicit loopback TCP connection for the existing protocol-1 identity challenge and authenticated hook POST. Checks state MAC/key ID, nonce/event/identity/expiry/proof, rereads state/key, and rejects generation changes before POST. There is no connection pool, proxy, redirect, downloaded runtime, or new network dependency. |
| Output | Passes through the existing valid object response and normal exit 0. It does not suppress PostToolUse output. The UTF-8 reader stops at the original 1,000,001 decoded-character ceiling even when a writer remains open. Unsupported input shapes use the original Python reader and bridge before any native hook POST. |
| Deadline | Captures the original 8-second transport/recovery/local-execution budget before identity work. After input completes, an expired budget prevents native sending. Native daemon I/O uses at most 2 seconds of what remains, recomputes its remaining timeout after each partial write, and preserves the Python reader's final budget check after a complete body. Failure completion retains the same absolute Linux CLOCK_MONOTONIC deadline and existing 3-second recovery/8-second fallback caps. As in the frozen bridge, stalled stdin and stdout backpressure require the harness outer process supervisor. Already-received terminal output has no new final deadline gate. This is not an absolute 8-second wall-time completion guarantee. |
| Failure completion | Uses sealed anonymous memory bounded to 8 MB and `exec` into the verified installed Python helper. No request is written to a persistent file or argv. The helper completes the existing bridge branch; only a handoff explicitly made before any native hook POST may enter the original bridge from its start. Current auth failure, overload, recovery and local fallback behavior remain owned by the existing bridge functions. |
| Containment | `exec` preserves the harness-owned PID and process group. Existing Python recovery and fallback continue to use the existing isolated process runtime. |

`tests/fixtures/claude-launcher-pilot-auth.json` contains deterministic synthetic vectors produced from the immutable Python auth module at `ae33987d0c8675c36a77375e03419aee920825f6`, including its original SHA-256. Its regeneration script reads that exact git object. The native canonicalizer matches Python's sorted, compact, ASCII-escaped JSON, including Unicode surrogate-pair encoding. The tests exercise exact challenge identity, nonce, event, key and lifetime checks.

The initial native HTTP reader covers the explicit Content-Length HTTP/1.0 and HTTP/1.1 responses emitted by the current daemon. `localhost`, noncanonical input text and shapes outside the two declared events use the existing Python bridge before a native hook POST. Numeric IPv4 and IPv6 loopback state can take the native path. Unsupported HTTP framing remains a conformance gap until its exact failure behavior is tested. Exact timeout reason text is also unqualified: native completion uses the outer bridge's generic timeout wording, while Python may surface a phase-specific HTTP timeout before its outer queue expires. The existing recovery/fallback branch and deadline are retained; this pilot does not claim every malformed-listener or timeout-detail outcome is equivalent.

Current evidence is source conformance only. Real native and frozen-Python processes exercise both events against an actual TCP listener with synthetic authentication: allow, block, review, incorrect proof, expired challenge, changed state, changed key, malformed response, valid early EOF and invalid early EOF. The listener verifies that challenge and hook POST use the same connection. Additional cases cover private install/restore/reactivation, mandatory-native failure accounting, exact CRLF byte limits, UTF-8 character limits while the writer remains open, and empty/partial stalled input. The frozen Python HTTPResponse body readers and the native reader also share deterministic complete/empty/early-EOF deadline witnesses; native partial writes and regular-file-to-FIFO races have bounded executable tests. The source fixture replaces only the installer's wheel-membership lookup and uses an exact owned interpreter copy; native MAC, registration, file and self-identity checks still execute in the real native process.

The retained evidence distinguishes superseded attempts from the final implementation. The first debug process matrix had 23 passes, one outer 10-second timeout in expired PreToolUse, and 11 unreached cases; startup cost was not separately profiled. A subsequent 68-test release suite passed in 135.03 seconds before review found CRLF normalization, and the corrected 71-test suite passed in 118.42 seconds before review found the HTTP completion/partial-write and FIFO-open edges. Those earlier working-tree snapshots were not frozen and do not identify the final candidate. The final corrected suite passed **81 Python tests in 114.04 seconds** and **12 Rust tests**. Release Clippy and focused Ruff checks passed. The permanent authority gate against release base `4b89e0d2d`, the Python semantic callgraph gate (12 roots), and the Python I/O ownership gate passed with no new policy exceptions. The [component report](claude-component-evidence.json) records the rebuilt binary and all implementation file hashes. Local capabilities explicitly identify a development build (`0.1.0`, build `unknown`); actual wheel identity remains a separate installed requirement. The [stdin evidence](claude-stdin-conformance.json) retains each real Python/native stalled-input result. No failed or unreached attempt supplies a successful timing comparison.

Installed wheel selection and route conservation, installed registration repair/restore, source/Watch/availability/approval faults, CPU/resource attribution, and paired cold/warm comparisons remain separate gates. Component success does not close RSP-073 through 084 or PRD Phase 2.

No native launcher benefit or no-go is established yet. Earlier paired installed baseline failures are preserved as failures, not evidence that Python startup is inexpensive. The next comparison must use an actual installed candidate and its original registered Python baseline with the same prepared daemon, exact response/exit semantics, native route counts, source scope and failure samples. The original 30% improvement and at-most 5% other-metric regression rule, latency targets, sample counts, four-platform/frozen/signing qualification and upgrade/rollback requirements remain unchanged. Windows source-reference refusal cannot supply successful full-review or timing coverage; this Linux pilot adds no Windows secure-opening behavior.

The private installed comparison is `scripts/bench_claude_native_launcher_pilot.py --wheel CANDIDATE_WHEEL --json REPORT`. It requires the exact installed wheel digest and no development overrides, starts the normal daemon fixture, checks benign/block responses and native receipts for both events, and measures five alternating Python/native blocks with 30 real process launches per arm by default. Linux reaped launcher CPU and the separate daemon process tree are reported together without load-generator CPU. Registration switches and file authentication for selection occur outside sample timing; the native process's complete record/package hashing, transport, any terminal completion and exec time remain inside every sample. Failed attempts and partial latencies remain in the report and denominator accounting; incomplete cells cannot supply a comparison, and completed cells are checkpointed. The reported point estimates do not establish uncertainty or release tail gates.

This workspace still rejects the normal native daemon's AF_UNIX socket creation. A synthetic authenticated listener is used only for component conformance; it cannot replace installed daemon receipts or produce an installed performance decision. The source diagnostic interpreter copy preserves exact original executable bytes while satisfying the pre-existing current-user/root ownership requirement. Its original and copied ownership/digest evidence is retained separately.

The hosted probe signs `require_native_transport=true` into its private registration record. A native sample that would enter Python completion is an explicit nonzero failed attempt; it remains in failure accounting and cannot supply a successful native-launcher measurement. Ordinary component conformance uses `false` and retains the original failure/recovery path. This distinction is controlled by the private installer and authenticated record, never by a hook payload or environment variable. The initial input conformance scope is Linux UTF-8 with the existing surrogateescape behavior; alternate interpreter input encodings remain unqualified.

The subsequent integration checkpoint adds a mandatory independent Linux installed-wheel probe to the paired builder. All four platform selections and continuation after a failed paired sampler pass the 27-test builder/runner set. A targeted type check then found seven errors in the private Python handoff wrapper; explicit bridge keywords and exact integer validation for status/errno correct them. The 43 focused handoff/probe/deadline tests and targeted type gate pass. The [integration validation](claude-pilot-integration-validation.json) retains the initial lint/type failures and final file hashes. The original 81-test component report remains unchanged and describes its earlier exact snapshot; these focused tests do not relabel it as a complete native rerun of the later helper. Actual installed performance remains pending.
