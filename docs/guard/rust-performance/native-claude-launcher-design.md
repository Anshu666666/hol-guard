# Dormant native Claude launcher pilot

Status: reviewed design with an initial dormant source implementation; no registration change or default activation is included. This supports RSP-074 and preparation for RSP-075. It does not complete either task or their dependencies. Original source reviewed: `e3902da354517b6ba3116fc2d17a7b6e1b4f8d6b`. PRD and TODO requirements, thresholds, and task states are unchanged.

The first candidate is a transport-only Claude Code `PreToolUse` / `PostToolUse` launcher inside the existing bundled `hol-guard-runtime` executable. It would send the same bounded hook body through the existing authenticated daemon endpoint. The daemon would continue to own policy readiness, native request construction, source-reference admission, Watch, review registration/reuse, receipt persistence, and response rendering. The launcher would never invoke the Rust one-shot semantic evaluator or a Python hook oracle.

## Proposed argv and package binding

The dormant command is:

```text
<absolute bundled hol-guard-runtime> claude-launcher-v1 --config <absolute private config> --config-sha256 <64 lowercase hex> --event PreToolUse|PostToolUse
```

Only an explicit local/admin preparation command creates the config and returns this vector for an isolated private fixture. It does not update live Claude settings. Hook input and environment variables cannot enable the pilot, select another binary, replace the config, widen its event set, or choose another endpoint. The command is compiled only with `--features native-claude-launcher-pilot`; default wheels do not advertise its `claude-launcher-pilot-v1` capability.

The versioned config contains the schema, canonical guard-home/home/workspace context, exact encoded hook query, bundled runtime path, runtime size/SHA-256, manifest SHA-256, package version, separate capability platform and Cargo manifest target, build SHA, rule digest, and the admitted daemon compatibility/package/source-root/runtime-fingerprint identity. A proposed 16 KiB total bound fits the existing runtime manifest class; oversized contexts reject preparation. There are no tokens, payloads, fallback commands, arbitrary URLs, or shell fragments in the config. The argv digest binds its exact bytes.

Preparation uses the existing complete bundled-runtime inspection with attestation reuse disabled and rejects developer overrides, loose binaries, and incompatible capabilities. Execution verifies the private config through one retained file handle, checks its byte hash and exact schema, and checks the current executable and sibling manifest against the recorded package identity. A path/stat-only cache is not sufficient. Measuring the full executable hash is part of the pilot cost; it must not be omitted from installed timing.

For the first isolated experiment, discovery must match the recorded exact daemon identity. This is a declared narrower admission than existing same-version/newer-Desktop sharing. The pilot must not retire a newer daemon, rewrite its identity, or silently switch package roots. Supporting Desktop sharing requires a separately reviewed port of the existing peer rules and installed upgrade tests.

An upgrade, moved package, replaced manifest/runtime, or changed admitted daemon identity makes the old pilot registration stale. Repair must regenerate config/argv from the newly validated package. Later registration work must use exact managed-handler identity, preserve foreign hooks, replace only Pre/Post, remain idempotent, and survive SessionStart refresh. The current five-group sync cannot simply be pointed at a Pre/Post-only binary. RSP-076 remains a separate gate.

## Protocol and authority

1. Establish one absolute monotonic deadline at process entry. Read at most 1,000,001 stdin bytes; reject excess, invalid UTF-8, duplicate JSON keys, non-object input, excessive depth, or a noncanonical/mismatched event. Empty/missing-event/alias behavior needs explicit negative vectors; it is not guessed as allow. Preserve the original admitted hook object and nested values when forwarding, including `guard_remaining_ms`; do not normalize a command, shorten output, or erase ancillary input.
2. Open `daemon-discovery-key` (at most 256 bytes) and `daemon-state.json` (at most 64 KiB) with read-only, retained-handle ownership/privacy/type/link checks. The launcher never repairs their permissions. Verify protocol/key identity and HMAC over **all signed fields**, removing only `state_signature`. The existing signature recipe is sorted compact JSON with Python `ensure_ascii=True`, not the native receipt canonical JSON recipe. Unicode paths, surrogate escaping, integer/float representations, and unknown signed fields need paired producer vectors before support is claimed.
3. Validate canonical guard-home, loopback host, port, process/state identity, and the admitted package identity. Connect directly to an admitted numeric loopback address. No proxy, redirect, DNS, bearer-token fallback, or endpoint from stdin is permitted. Initial profile supports `127.0.0.1` and `::1`; legacy `localhost` requires an explicit bounded resolution contract before admission.
4. Generate a fresh 32-byte random nonce. On one TCP connection, POST `/v1/daemon/identity-challenge` with protocol version, nonce, state ID, and the configured canonical event. Verify the signed response against nonce, event, host/port/PID/start time, guard-home and state ID; enforce existing 1,000 ms future skew and 5,000 ms maximum challenge lifetime. Re-read signed state/key and compare the generation tuple and key before sending hook material.
5. Reuse that exact socket for POST `/v1/hooks/claude-code?<prepared query>` with `X-Guard-Daemon-Nonce` and `X-Guard-Daemon-Proof`. The server consumes the nonce once and checks event, proof, expiry, and connection identity. The launcher must not pool the socket across invocations or resend the hook after any possibly delivered write.
6. Bound response status line/headers and checked content length independently of the 1,000,000-byte body limit. The narrow client can admit the server's explicit Content-Length framing; conflicting lengths, transfer encodings outside the admitted profile, interim/redirect responses, truncated bodies, or extra response frames fail transport validation. Every partial read/write uses the remaining absolute deadline. Challenge success requires HTTP 200; hook success requires HTTP 200 and one bounded JSON object.
7. Return the authenticated hook response with its fields intact and one trailing newline. Do not reinterpret allow/review/block, synthesize replacement output, strip approval metadata, or derive authority from a receipt writer acknowledgment. No hook payload, proof, token, path, or output is logged to stderr.

The daemon remains the only caller of the existing native resident decision path. Its control lease and ordinary review binding stay in effect. Source references are opaque transport fields: the launcher must neither open them nor create new references, change their digest, or widen `source_ref_external_allowed`. Watch is applied by the acknowledged daemon policy; the launcher cannot infer Watch from stdin or an environment marker.

## Deadlines, recovery, and unavailable outcomes

The initial proposal retains the 8-second launcher envelope, the existing 2-second authenticated-daemon attempt cap, and the installed 30-second Pre/Post harness timeout. Daemon work retains its existing clamp/reserves; no new timeout extends a prior deadline. Stdin stalls, short writes, socket stalls, and stdout backpressure require process-level containment tests on all three operating-system families. A blocked stdio helper may not outlive the launcher process, and a partial output cannot be counted as a successful harness response.

Successful authenticated daemon output, including native-unavailable, Watch, review pause/retry, post redaction and post continuation, is passed through. Transport unavailability is a separate boundary: the existing bridge may start the daemon and invoke an isolated Python CLI fallback; after failure its final ordinary availability result is a Pre allow warning and `{}` for Post. Those final mechanical responses do not require a semantic oracle. The pilot must preserve that availability policy while leaving automatic recovery unsupported initially.

For the **dormant warm-daemon experiment**, ordinary transport unavailability returns exactly the existing final event-specific availability shape: Pre has `continue=true`, `hookSpecificOutput.hookEventName=PreToolUse`, `permissionDecision=allow`, and the existing bounded warning message; Post returns `{}`. Exit remains zero. Size-limit failures retain the existing event-specific deny/block shape. Authentication/integrity failures retain the separate existing Pre deny / Post continuation-warning shape, and must not be relabeled ordinary unavailability. No local environment or hook field selects the classification. Source-generated golden fixtures freeze the exact messages, shapes, and failure categories before the Rust entry is wired. Authenticated Watch remains daemon-owned; an unavailable launcher does not invent a Watch mode. Lifecycle failures and missing recovery remain explicit unsupported paths and activation blockers, not a reason to change ordinary availability authority.

A later lifecycle recovery port may invoke only a package-bound administrative daemon-start command under existing isolation and the remaining budget. It may retry discovery/challenge before hook bytes were sent; it must never replay a possibly delivered hook, review registration, or approval consume. The lifecycle subprocess must be proven contained on Unix and Windows. Until that contract is implemented and qualified, daemon startup/recovery and unavailable Watch remain activation blockers. The experiment is allowed to report those cases as unsupported; it cannot exclude them from the eventual production acceptance matrix.

Reuse `ring`, `getrandom`, SHA-256 and existing strict JSON admission for signed state and request/config admission. Delivered hook responses need their own admission contract, because the Python bridge forwards opaque JSON objects that exceed native request parser limits. The implementation uses the separate Windows `BoundReadFile` facade: it opens retained ancestor/file handles with read/inspect access, denies concurrent write/delete sharing, and validates identity after reading. Private authority files additionally require one link and verify-only parent/file ACL checks. Public package manifests permit cache hardlinks and ordinary package ACLs. Neither path invokes writer/repair primitives. Custom guard-home roots and inherited Windows discovery-file ACLs still need actual Windows qualification before claiming support.

The native resident framing/client is not an HTTP client and cannot replace the authenticated daemon endpoint. The narrow HTTP client should either reuse an already reviewed suitable parser or implement only the frozen daemon framing profile with independent adversarial vectors. No HTTP library is currently a direct dependency of `guard-runtime`; adding one would require lockfile/license/source review. No custom cryptography is needed.

## Required validation and decision gates

The semantic matrix must include canonical Pre allow, native block, initial review pause, approved retry, revoked approval/control, Watch allow, native unavailable, and canonical Post benign, secret block/redaction, Watch preservation, failed tool output, source references, malformed/oversize output, exact size edges, and Unicode/context paths. Compare native route receipts and final harness output independently; a locally synthesized safe response cannot satisfy native-route evidence. Test stale manifest/package/config, wrong key/signature, state replacement between challenge and hook, expired/reused/wrong-event/wrong-socket proof, pre/post-dispatch disconnect, capacity rejection, timeout, short I/O, proxy environment, malicious cwd, and no Python process on the successful warm path.

The performance experiment must use paired installed baseline/candidate wheel identities and actual generated argv. Retain Python launcher baseline and native pilot observations separately, including failures. Include executable hashing, process start/exit, stdin/stdout, discovery, authentication and daemon work. A diagnostic phase run may use startup/import tracing but cannot be mixed into headline timing. Report CPU, allocations, peak RSS, and resource/process containment as well as latency. Do not subtract p95 values to claim phase savings.

Full qualification retains the PRD sample counts, five independent process runs, 50/100 ms warm targets, 200 ms concurrency-16 p99, cold/readiness/recovery/resource budgets, unchanged correctness limits, and four wheel platforms. The current two-observation smoke reports do not satisfy any proposed activation criterion. No default registration change is authorized by this document.

Open prerequisites are concrete: actual harness-use ranking; golden verification of the unchanged availability/authentication classifications and Watch results; administrative recovery containment; canonical JSON parity for the complete signed state domain; Windows read-only discovery ACL compatibility; package/daemon peer compatibility during upgrades; bounded HTTP/stdin/stdout behavior; and installed differential benefit. These remain visible acceptance blockers rather than silently narrower production guarantees.

## Initial dormant source tranche

The checked-in [config schema](../../../contracts/launchers/claude-native-launcher.v1.schema.json) and [Python reference fixtures](../../../contracts/launchers/claude-native-launcher.v1.fixtures.json) bind the explicit profile. The fixture generator calls the existing Python response/discovery helpers and records their source hashes. It includes 16 final response cases, 60 HTTP classifications, four transport/size exception classifications, three Unicode state/challenge pairs with unknown nested signed fields, 30 actual hook-object cases and 20 actual Python HTTP wire cases. The initial state-load wrapper preserves the legacy stage distinction: initial discovery errors become ordinary availability; a failed contacted proof or subsequent state/key reread becomes authentication failure. HTTP overload classification retains its existing precedence. Actual connection/read failures preserve ordinary availability; an empty EOF after an admitted 401/403 status preserves authentication failure as Python does. Framing that Python can accept but the pilot does not implement is explicitly unsupported and produces the existing event-specific deny/block shape with a fixed pilot-profile reason; it must never turn a possible daemon denial into an availability allow. This stricter unsupported-domain behavior is an activation limitation, not a claim of complete transport parity.

The Rust source uses the existing `ring` HMAC and strict JSON admission for signed state and requests. It explicitly rejects signed floats, out-of-range integers and lone surrogates; it does not claim full Python signed-domain parity. Delivered hook objects use separate bounded admission: UTF-8 replacement and whitespace stripping match the Python bridge, while accepted response bytes are preserved without reserialization. Wide arrays, duplicate object members and depth-64 fixtures are supported. Nonfinite/overflowing numeric values, unpaired surrogate escapes and recursion beyond the admitted parser profile produce explicit unsupported-response blocks. Genuine malformed JSON retains the legacy availability result. The wire parser accepts equal duplicate lengths; chunked/EOF framing, conflicting lengths, informational responses, noncanonical status spacing/version, header bounds and other unsupported wire domains never become availability allows. The explicit preparation helper invokes full installed runtime validation with attestation reuse disabled, requires bundled auto mode plus the pilot capability, and leaves harness settings unchanged.

This is source/component evidence only. It has no installed candidate latency result, paired speedup, real daemon challenge/Watch/review/source-reference lifecycle qualification, process-level stalled-stdio containment proof, or Windows/macOS installed proof. The source feature remains off by default, and no production registration helper selects it. These missing results continue to block activation and completion of RSP-075.
