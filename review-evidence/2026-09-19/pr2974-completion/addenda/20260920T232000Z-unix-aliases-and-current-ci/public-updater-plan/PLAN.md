## Actual product chain

1. `commands_dispatch_local._run_guard_update_command` constructs the real GuardStore/context and calls `update_driver.run_guard_update`. It independently respects managed install ownership. Invoke this public CLI from its installed interpreter, outside the source checkout, with explicit private home, Guard home, workspace and the exact wheel file.
2. `run_guard_update` loads the real machine policy, builds the trusted subprocess context, queries the installed distribution and stages the requested wheel. Explicit wheels still go through version-source handling; they do not bypass installation identity or protected downgrade checks.
3. `_authority_blocks_downgrade` compares actual package versions. A lower version is refused if authority health is anything other than UNENROLLED, including protected, tampered and degraded states. The refusal precedes installer command construction/execution. A synthetic fake wheel or patched current version would test a control, not qualify an actual installed downgrade.
4. `update_artifact` copies into an owned private staging root and revalidates entry, metadata and bytes immediately before the real installer. `TrustedUpdateContext` binds the interpreter, import roots, installer and neutral directories; pip runs isolated with an explicit trusted index. `update_install_verify` checks installed metadata/code version agreement.
5. `_execute_update` retains original installer outcomes and original bounded product retry behavior. It invokes daemon refresh through the trusted fresh interpreter, then package shim refresh and managed harness repair. If a daemon existed before the update and verified refresh fails, the update remains failed even if package replacement succeeded.
6. The actual refresh program attempts retirement/restart under its existing limits: at most three product attempts, original five-second retirement polling, original post-update startup allowance and stability checks. Manager retirement binds the owned daemon identity, uses SIGTERM then its existing SIGKILL path on POSIX, and requires affirmative retirement completion. A listed PID or return from a stop helper alone is not death proof.
7. `update_harness_repair` repairs the actual recorded Codex/Cursor/Grok/Pi/OMP/OpenCode registrations through the new installed interpreter. It is not an Ollama extension-catalog installer. Ollama catalog, control revision, program digest and native receipt continuity must be checked separately.
8. Existing session/operation HTTP endpoints persist active session and started operation records; `resume_session` reads them back. Daemon `clear_runtime_state` deletes its own runtime row, not the separate guard session/operation tables. This supports a meaningful persistent active-session continuity fixture. It does not prove that an HTTP/native request was executing across retirement.

## Smallest first fixture

Use a fresh disposable Linux runner, one nonroot owned prefix, one private home/workspace/store and original local files only. No development runtime override, Python semantic oracle, altered updater function or copied product source import is admitted. The installer bootstrap may install the predecessor and a separately locked dependency closure before the observation begins; every measured transition must then enter through the actual public updater. Record the initial bootstrap separately.

An explicit wheel update can reinstall dependencies. The product deliberately drops ambient PIP/UV configuration and accepts only an HTTPS package source. Therefore a local file index or `PIP_NO_INDEX` environment trick is not a valid plan. Prepare a finite hash-locked dependency wheelhouse for both actual wheel METADATA sets and expose only that closure through an owned loopback HTTPS simple index. On a fresh disposable Linux VM, use the real root-owned `/etc/hol-guard/managed-policy.json` and a bounded fixture CA through the documented machine policy fields: user install/update ownership, explicit index URL, public registries disabled and proxy mode none. This is a fixture TLS trust root, not release signing authority. Refuse an existing machine policy/cache; retain before/after identities and remove only the exact fixture-owned files. Do not change a user machine, ambient global configuration or persistent runner. The exact dependency closure, HTTPS fixture, certificate validation and policy cleanup require separate controls and peer review before execution.

Keep the selected registered request finite and already described by a strict installed delivery/native-receipt oracle. Select its exact harness/event/payload and public-install command during implementation, then freeze those inputs before the source/operational peer. The plan ceiling is one registered request plus one original Ollama review at each of A0/U1/U2/U3 (eight workload requests total), with no automatic retries. Setup/authority/session calls are separately enumerated, not counted as native workload. If an existing original helper adds a product request, enumerate it before launch rather than excluding it from the count.

Use the existing generated-key encrypted-file authority fixture only for private CI enrollment, verified again through a fresh unmodified installed GuardStore. Preserve its `interactive_enrollment_qualified=false` limitation. A protected authority state must remain protected across every same-version replacement; never delete authority rows or keys to make rollback pass. Choose a compatible unchanged catalog/program for this first test, and retain their exact equality rather than claim a program upgrade.

The session record stays active and its operation stays started while U1/U2/U3 execute; after each transition, resume it through the actual authenticated endpoint and compare immutable identity/context/state. This tests durable session continuity, not an outstanding request. It must not be relabeled as the live in-flight clause.

Each phase starts only after the previous phase's original outcome, strict native/durable evidence and owned containment are admitted. On any failure, stop later transitions, retain partial state and original result, and perform only the reviewed owned cleanup. Do not delete a prefix/store while ownership or child containment is uncertain. Same-process stale imports are not allowed to validate the replacement; use a fresh installed interpreter for after checks. Original updater internal limits/retries remain untouched, and original registered/native deadlines remain unchanged. An outer containment ceiling must be set from these known limits and separately reported; it is not a product latency target.

## Controls and retained proof before any launch

The implementation should use meaningful negative controls for wrong build/tree/wheel/runtime/RECORD, a mismatched package version, mutable staging input, hostile inherited installer environment, an untrusted or changed HTTPS/policy/CA source, missing protected authority material, false daemon retirement, stale repaired registration, lost active session/operation, a native availability fallback mislabeled as evaluation, lost/duplicate committed receipt, and cleanup uncertainty. A pure forwarding control must prove the actual public updater call is made once with original arguments and its return/error retained. Test the protected-lower-version refusal with an installer sentinel only as a local control; actual downgrade qualification still needs the genuine pair.

The driver contract must bind original task clauses, product and actual build identities, every archive/member/wheel/runtime/manifest, both dependency closures, installer/interpreter identity, the exact three transition argv, selected fixed requests, and all setup/control counts. Refuse null placeholders before any environment or subprocess action. Preserve raw bounded stdout/stderr and private evidence locally, exporting only declared fixed facts/digests; do not upload keys, tokens, credentials or unbounded private payloads. Keep original failure, diagnostic completeness and broad qualification as separate fields. A strict final reader must reject missing offered/terminal/after/cleanup records, unexpected extra requests, non-native success and any unproven current identity.

Only after the concrete source/control and operational/input peers are clear should one isolated Linux functional fixture be considered. This preparation itself creates no launch ref. The three other platforms, real version pair, in-flight boundary and signed/frozen paths are explicit later cells, not automatic retries or a blanket campaign.
